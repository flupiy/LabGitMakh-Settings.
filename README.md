# LabGitMakh-Settings.
«Лабораторная работа по настройке репозитория».
«Учёт студентов колледжа» (учебный репозиторий).
Назначение проекта
Проект служит учебной площадкой для отработки ключевых практик работы с Git и организации структуры репозитория в .NET‑проектах. В рамках проекта решаются следующие задачи:

Отработка структуры репозитория и правил Git — настройка .gitattributes и .gitignore для корректной работы в смешанной среде (Windows + кроссплатформенные инструменты).
Работа с C# и WPF — реализация базовой логики учёта студентов (класс Student, обработка данных, UI на WPF). Это напрямую связано с твоими предыдущими задачами по отладке кода и подготовке тестовых сценариев.
Подготовка тестовых сценариев и протоколов совещаний — ведение документации в docs/, фиксация результатов тестирования в build/, логирование в logs/ — чтобы история изменений отражала не только код, но и процесс разработки.
Разделение артефактов — чёткое разделение исходного кода, документации, результатов сборки, логов и временных данных для чистоты истории коммитов и удобства CI/CD.

Описание структуры каталогов
В проекте используется логическое разделение по назначению файлов.

Каталог src/ хранит весь исходный код приложения — в нём лежат файлы вроде Program.cs, классы (например, Student.cs), а также компоненты WPF‑интерфейса. Это основная рабочая зона для написания и отладки кода, включая исправление ошибок вроде нехватки поля book в MainWindow.

В папке docs/ размещается документация и материалы процесса разработки: краткое описание проекта, инструкции, протоколы совещаний, методические указания. Сюда же удобно складывать формулировки практических и индивидуальных заданий по классу Student, чтобы они были под рукой и версионировались вместе с проектом.

Папка build/ предназначена для артефактов сборки и результатов тестирования — например, отчётов, чек‑листов, итоговых файлов вроде result.txt. Такое разделение помогает не смешивать код и результаты его работы, а также упрощает автоматизацию.

В каталоге logs/ хранятся журналы работы приложения — например, файл app.log с записями разных уровней (INFO, DEBUG и т. п.). Логи нужны для анализа поведения приложения и отладки, но не должны засорять историю коммитов.

Папка temp/ используется для временных файлов и кэша — например, cache.tmp с временными метками и статусами. Эти данные генерируются во время работы и не являются частью исходного кода.

В корне репозитория находятся конфигурационные файлы: .env с переменными окружения (например, APP_MODE=Development), .gitattributes с правилами обработки файлов и .gitignore со списком игнорируемых данных.

Перечень типов файлов, исключаемых из отслеживания (.gitignore)
Чтобы репозиторий оставался чистым и безопасным, из отслеживания исключают:

артефакты сборки — папки bin/ и obj/, файлы *.dll и *.exe: они генерируются при сборке и не нужны в истории;
временные и кэш‑файлы — содержимое temp/ и файлы с расширением *.tmp: они меняются при каждом запуске и не несут смысловой нагрузки для версионирования;
логи — все файлы в logs/*.log: они быстро разрастаются и отражают текущее состояние, а не стабильную функциональность;
пользовательские настройки и секреты — файлы вроде .env (если в них есть реальные значения), user.config: их не стоит хранить в публичном репозитории из соображений безопасности; при этом шаблон .env без секретов можно оставить, чтобы другие участники могли быстро развернуть окружение;
файлы IDE — папка .vs/, а также файлы *.user и *.suo: это персональные настройки Visual Studio, не относящиеся к самому проекту;
архивы и тестовые наборы данных — файлы *.zip и *.7z, если они большие или генерируются автоматически: их лучше хранить отдельно или скачивать по мере необходимости.

Сведения об использованных настройках репозитория (.gitattributes)
Файл .gitattributes задаёт правила, по которым Git обрабатывает файлы. Это помогает избежать проблем с окончаниями строк и некорректным сравнением бинарных файлов.

Правило text=auto позволяет Git автоматически определять, является ли файл текстовым. Если да — к нему применяются правила нормализации, если нет — файл считается бинарным и не изменяется. Это удобно, когда в репозитории много разнородных файлов и не хочется прописывать каждый тип вручную.

Для файлов C# (*.cs) установлено правило text eol=crlf. Это означает, что окончания строк будут в формате Windows (\r\n). Такой выбор оправдан, если основная разработка ведётся в Visual Studio на Windows: это снижает риск ложных изменений в диффах и делает работу комфортнее.

Файлы Markdown (*.md) и текстовые файлы (*.txt) настроены как text eol=lf — с окончаниями строк в формате Unix (\n). Это стандарт для документации на GitHub, а также для CI‑систем и Linux‑серверов. Благодаря этому описания, отчёты и протоколы отображаются корректно вне зависимости от ОС.

Изображения (*.png, *.jpg), PDF‑документы (*.pdf) и архивы (*.zip) помечены как binary. Git не пытается сравнивать их построчно и не применяет к ним преобразования. Это защищает файлы от повреждения: картинка не станет нечитаемой, PDF не перестанет открываться, а архив — распаковываться.

Такие настройки особенно важны в твоём проекте, потому что ты активно работаешь с кодом (C#, WPF), документацией (протоколы, задания), логами и артефактами. Правильная конфигурация Git делает совместную работу предсказуемой и избавляет от лишних конфликтов.
